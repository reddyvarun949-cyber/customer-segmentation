# Customer Segmentation

**Methods practised:** clustering — k-means, elbow and silhouette, hierarchical clustering, DBSCAN, PCA for
visualisation, stability with the adjusted Rand index (B1 Module 09); log transform and scaling in a pipeline
(Module 05); exploratory and result plots (Module 03); saving a model and serving it through a simple API (Module 13).

## Problem statement

*FreshCart*, a fictional online grocery store, sends the same offers to every customer. Marketing wants to split
customers into a few **segments** with similar shopping behaviour, so each group gets a message that suits it.

There is **no target column**. This is **unsupervised learning**: we turn one year of orders into seven behaviour
features per customer (RFM + coupon use, app use and category variety), let k-means group similar customers, then study
the groups and give them business names and suggested marketing actions.

**Expected result:** a small number of segments that are clearly different, stable when the algorithm is re-run, and
easy to explain; an API that places a new customer into a segment and explains how they compare to it; and a web page
that shows all segments. (The build run's actual numbers — number of segments, sizes, silhouette and stability scores
— are in `VERIFICATION.md`, `models/segment_profiles.json` and the executed notebook.)

## Dataset

Synthetic data generated by `data/generate_data.py`: an `orders` table (one row per order) and a `customers` table
(one row per customer). Each customer was secretly given a shopping style when the data was generated, but that style
is **not** in the files — just as in real life nobody hands you the "right" segments. See
[data/DATA_DICTIONARY.md](data/DATA_DICTIONARY.md) for every column, the messiness added on purpose and the formulas
of the engineered features.

## How to run (three terminals)

**1. Python environment and notebook** (from this project folder):

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
jupyter notebook notebook/Customer_Segmentation.ipynb     # Run All: this creates models/
```

The trained pipeline is already included in `models/`, so you can skip straight to step 2 if you only want the app.

**2. Backend API** (same environment, from this project folder):

```bash
python backend/app.py                 # http://localhost:5000
python -m unittest discover -s backend -p "test_*.py" -v    # optional: run the tests
```

Try it without the frontend:

```bash
curl http://localhost:5000/api/health
curl http://localhost:5000/api/segments
curl -X POST http://localhost:5000/api/segment -H "Content-Type: application/json" \
  -d '{"recency_days":15,"frequency":12,"monetary":5400,"avg_basket":450,"coupon_rate":0.9,"app_share":0.8,"category_variety":3}'
```

**3. Frontend** (needs Node.js 18+):

```bash
cd frontend
npm install
npm run dev                           # open http://localhost:5173
```

If the API runs somewhere else, copy `.env.example` to `.env` and change `VITE_API_URL`. If the frontend runs on a
different address, start the backend with `FRONTEND_ORIGIN=http://that-address python backend/app.py`.

## Architecture and request flow

```
 Browser (React page)                  Flask API (backend/app.py)                     models/
 ────────────────────                  ──────────────────────────                     ───────
 page opens ── GET /api/segments ───▶  return profiles (loaded at start-up) ◀──────── segment_profiles.json
            ◀── 5 segment cards: name, description, action, size, medians, valid ranges
 user submits ─ POST /api/segment ──▶  1. parse JSON (400 if not JSON)
   {recency_days, frequency,           2. validate each field + cross-field rules (422 + per-field messages)
    monetary, avg_basket, ...}         3. one-row DataFrame → pipeline.predict / transform ◀── segmentation_pipeline.joblib
                                       4. look up name/description/action, compare with segment medians
            ◀── 200 {segment_id, segment_name, description, suggested_action, fit, comparison[...]}
 highlights the matching card, shows the action and an above/below/close table, or the error next to the field
```

- The pipeline is **trained once in the notebook** and loaded **once when the API starts**. Requests only call
  `predict` (nearest segment centre) and `transform` (distances to all centres).
- The saved object is the **whole pipeline**, so the log transform and scaling are applied exactly as during training.
- `fit` is `"borderline"` when the nearest centre is almost as far as the second-nearest (distance ratio > 0.8).
- The frontend computes `avg_basket = monetary / frequency` itself; the API checks that it matches.

### API reference

| Method | Path | Request | Success response | Errors |
|---|---|---|---|---|
| GET | `/api/health` | — | `{"status": "ok", "model": "...", "segments": n}` | — |
| GET | `/api/segments` | — | `{"model", "customers_clustered", "silhouette", "features", "valid_ranges", "overall_medians", "segments": [{"id", "name", "description", "suggested_action", "customers", "share", "medians"}]}` | — |
| POST | `/api/segment` | JSON with the 7 features | `{"segment_id", "segment_name", "description", "suggested_action", "fit", "distance_ratio", "comparison": [{"feature", "label", "value", "segment_median", "position"}]}` | 400 body not JSON; 422 `{"error", "fields": {field: message}}` |

Validation rules: all 7 fields required and numeric; `recency_days`, `frequency` and `category_variety` must be whole
numbers; every value must be inside the range in `valid_ranges` (recency 0–365, rates 0–1, variety 1–7, frequency and
spend up to the largest values seen); `category_variety` cannot exceed `frequency`; `avg_basket` must equal
`monetary / frequency` (within 1%).

## Ideas to extend

- Try a Gaussian Mixture Model and show each customer's probability of belonging to every segment.
- Normalise frequency and spend per active month, and re-run the segmentation every month to track movement between
  segments.
- Add an endpoint that takes raw orders for one customer and computes the 7 features itself.
- Add a scatter plot of the segments (PCA coordinates exported by the notebook) to the frontend.
- A/B test one suggested action against the old "same offer for everyone" approach.
